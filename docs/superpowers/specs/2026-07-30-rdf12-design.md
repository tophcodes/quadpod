# RDF 1.2 on the Wire — Design

**Date:** 2026-07-30
**Status:** Proposed (pre-implementation)
**Author:** Christopher Mühl (with Claude)
**Parent spec:** [2026-07-24-sparql-solid-pod-design.md](2026-07-24-sparql-solid-pod-design.md) §3, §4, §13
**Origin:** [2026-07-30-shape-validation-design.md](2026-07-30-shape-validation-design.md) §2.1
deliberately left one question open — whether this pod should speak RDF 1.2 at all — after
discovering that the SHACL dependency had switched the capability on underneath the non-goal.
This is that question, taken up and answered yes.

## 1. What is decided

**The pod speaks RDF 1.2.** The root spec's §3 non-goal — *"No RDF-star / RDF 1.2 on the wire —
Solid is RDF-1.1-anchored"* — is reversed, not qualified. §16 gains **ADR-6** recording the
reversal; §13's fourth success criterion is restated as a capability list (§8 below).

The non-goal is stated in **two** places, and both are amended. §4's key-decisions table carries
it a second time, with the rationale that actually did the work:

> **Strict RDF 1.1 everywhere; provenance is app data** — *"Backend-pluggability and RDF-star
> are mutually exclusive (not all stores support RDF-star)."*

That premise is what §8 dissolves: pluggability and RDF 1.2 are not mutually exclusive once the
criterion names a capability instead of a product class. **Only the first half of that row
falls.** *"Provenance/PROV-O is not a server concern — pipelines write it as ordinary triples"*
is a separate decision about what belongs in a server, it was never a consequence of the version
choice, and nothing here touches it. A pod that can store a triple term still does not mint
provenance; its writers do, as before.

The reversal is cheap to state and worth stating precisely, because the non-goal was never
false and never enforced. It held because nothing in the dependency graph had enabled
oxigraph's `rdf-12` feature. When `rudof_lib` arrived it did, and the non-goal became a claim
the code contradicted. Shape validation closed that with a refusal at the parser. This design
reopens it deliberately, having measured what the refusal was actually protecting.

## 2. What RDF 1.2 adds, measured

RDF 1.2 adds **two** new kinds of term, not one. This matters more than anything else in this
document, because the refusal built by shape validation covers one of them.

| Addition | Shape | Refused today? |
|---|---|---|
| **Triple terms** | an RDF triple in the object position of another triple | yes — `Format::parse` rejects `Term::Triple` |
| **Directional language-tagged strings** | a literal with a base direction, `"x"@en--ltr` | **no** — it is a `Term::Literal`, and nothing looks at `direction()` |
| Version announcement | media-type parameter, `VERSION` / `@version` directive | not read at all |

Measured in `oxrdf` 0.3.3: `BaseDirection`, `Literal::new_directional_language_tagged_literal`
and `Literal::direction` are gated behind the **same** `rdf-12` feature as the `Term::Triple`
variant. The feature that made triple terms parseable made directional literals parseable in
the same step.

The consequence for `docs/constraints.md` is direct. The rule *"The wire contract is RDF 1.1,
and it is checked rather than assumed"* was added with shape validation and is **half true**: it
pins a check on triple terms, and a directional literal walks past it into storage. It is
replaced rather than deleted — see §10.

### 2.1 The three version labels are the right vocabulary

[RDF 1.2 Concepts](https://www.w3.org/TR/rdf12-concepts/#defined-version-labels) (CR Snapshot,
2026-04-07) defines exactly three:

| Label | Meaning |
|---|---|
| `1.1` | RDF 1.1 syntax, without a version directive |
| `1.2-basic` | **RDF 1.2 syntax without triple terms** |
| `1.2` | full RDF 1.2 syntax |

and states the containment: *"Data conforming to version `1.1` is valid as data with version
`1.2-basic`, and data conforming to version `1.2-basic` is valid as data with version `1.2`."*

`1.2-basic` is not a curiosity. It is the exact name for the state this pod is in today —
directional literals accepted, triple terms refused — and it is the exact name for a backend
that can hold one and not the other. A two-valued capability could not express either.

### 2.2 Specification maturity, and what this pod is exposed to

Concepts is a Candidate Recommendation Snapshot of 2026-04-07. [RDF 1.2
Turtle](https://www.w3.org/TR/rdf12-turtle/) is a **Working Draft of 2026-07-23** — a week
before this design. Neither is a Recommendation.

This is a real risk and a bounded one. The pod does not implement the grammar; `oxttl` does. A
syntax change arrives as a dependency upgrade, not a redesign. The parts this design does
commit to — the three version labels and the `version` media-type parameter — are in Concepts,
the more mature of the two.

The `VERSION` / `@version` in-band directive is **not** a contract this design rests on. Turtle
is explicit that it is advisory: *"the version announcement is only a hint; this specification
does not mandate any parser behavior based on curVersion, but a parser MAY signal an error or a
warning."* The pod neither requires it on input nor derives anything from it. The media-type
parameter is the contract, because it is the layer where this pod already makes every other
representation decision.

## 3. The version vocabulary

```rust
enum RdfVersion { Rdf11, Rdf12Basic, Rdf12 }
```

Concepts' labels, in Concepts' containment order, with `PartialOrd` derived from that order.
One type serves three roles that would otherwise be three spellings of the same fact:

- **what a store can hold** — `SparqlStore::rdf_version()`
- **what a representation claims** — the `version` media-type parameter on the wire
- **what a deployment declares** — a remote backend's configured capability

The entire capability check is `needed <= store.rdf_version()`. Nothing translates between a
store-side vocabulary and a wire-side one, because there is only one.

### 3.1 A dataset has a version

`Dataset::rdf_version()` returns the least label under which every term in it is expressible:

- any `Term::Triple` ⇒ `Rdf12`
- otherwise any literal whose `direction()` is `Some` ⇒ `Rdf12Basic`
- otherwise ⇒ `Rdf11`

**This is the only place that classifies.** It replaces the `Term::Triple` check in
`Format::parse` — a check over one of the two additions — with a total one. Every question the
rest of this design asks about versions is asked of this function.

### 3.2 Capability belongs to the implementor

`rdf_version()` goes on `SparqlStore`, and each implementor answers it however it legitimately
can. This is not a table of backend names, which would be the "code change" §13 forbids; a new
backend is already a new implementor, so the answer rides on code that had to be written
anyway.

- `OxigraphStore` (embedded) answers with a constant. The feature is compiled in, so the store
  and its capability ship together.
- A future generic `RemoteSparqlStore`, pointed at Oxigraph-over-HTTP, Fuseki or GraphDB, is
  **one** implementor whose capability is a property of the endpoint rather than of its own
  code. It answers from configuration.

Considered and rejected: a marker subtrait (`trait Rdf12Store: SparqlStore`). It makes the
capability a property of the *type*, which is precisely what the remote case is not — one type,
two capabilities depending on config. `AppState` also holds `Arc<dyn SparqlStore>` (ADR-2), so
a subtrait would be reachable only through `Any` downcasting: a bool with ceremony.

Also rejected: deriving the constant from `cfg!(feature = "rdf-12")`. That tests a feature of
*this* crate; oxigraph's features are not visible from our code.

### 3.3 The crate declares the feature it depends on

`Cargo.toml` gains `oxigraph = { version = "0.5.9", features = ["rdf-12"] }`.

Today the feature is on only because `rudof_lib` reaches it transitively and Cargo unifies
features crate-wide. That is the same accident this whole design exists to retire: the pod's
entire ability to store what it has already stored would rest on a dependency's private choice,
and dropping SHACL — or `rudof` restructuring its own features — would silently take it away.
One line makes the capability a fact this crate states about itself.

It also needs no constraint rule, because the compiler already enforces it. `GroundTerm`'s
recursive variant (§7) converts from `Term::Triple`, and with `rdf-12` off that variant does not
exist. Removing the declaration is a build failure, not a silent regression — which is exactly
what the original non-goal lacked.

## 4. The wire contract: silence means 1.1

**A request or representation that does not name a version is treated as `Rdf11`.**

This is deliberately stricter than Concepts, which says that when no version is indicated
*"systems can assume the version is `1.2`"*. The deviation is stated here rather than buried,
and rests on two things:

1. §13's first success criterion is passing the Solid conformance suites. The suite is a 1.1
   client, as is every deployed Solid implementation the pod must interoperate with — rdflib.js
   and SolidOS, the Inrupt libraries, CSS. Following the spec's default would emit `<<( … )>>`
   to parsers that cannot read it, on requests that never asked for it.
2. Concepts' default is written for a world in which 1.2 is the ambient version. That world is
   not this one yet, and the cost of being wrong is asymmetric: a pod that is too conservative
   is merely less useful, a pod that is too eager is unreadable.

Concretely:

- **Write.** `Content-Type` without a `version` parameter ⇒ the body must classify as `Rdf11`.
- **Read.** `Accept` without a `version` parameter ⇒ the response is at `Rdf11`, degraded per §5.
- **Write and read at 1.2** are explicit acts, and symmetric ones.

`MediaType::parse` already preserves parameters — `;token=token` is inside the alphabet it
validates — so the parameter already reaches the boundary intact. What is new is reading it.
That is `RdfVersion::from_media_type`, and it is the **only** place `version=` is read, for the
same reason `ranked_accept` is the only place a q-value is parsed: the read side and the write
side ask the same question of the same syntax, and two readers are how they come to disagree.

Discoverability is a real gap and is **not** solved here. Under §4 a client must set
`version=1.2` to write triple terms, which it can only do if it knows the pod accepts them —
and Solid Protocol already requires `Accept-Put` and `Accept-Post` advertisement that this pod
does not yet emit. That is [issue #3](https://github.com/tophcodes/sparql-pod/issues/3), a
conformance fix worth making whether or not this design ships. This design fixes *what* those
headers must say about the version; it does not build them. Until they exist, a client learns
by `415`.

## 5. Read: degradation is asymmetric, and it is enumerated

The two additions do not lose the same way, and the design has to say so.

| Addition | Degrading to `Rdf11` |
|---|---|
| Directional literal | **strippable** — `"x"@en--ltr` becomes `"x"@en`; the triple survives, presentation metadata does not |
| Triple term | **not strippable** — the triple is omitted entirely |

A `GET` at `Rdf11` against a resource classifying above it answers **`200`** with the
projection, and says what it did. The `alternate` link names the resource's *own*
classification from §3.1 — `version=1.2-basic` for a resource whose only excess is directional
literals — because naming `1.2` there would promise triple terms that are not present:

```
200 OK
Content-Type: text/turtle;version=1.1
Vary: Accept
Link: <https://pod.toph.so/c/notes>; rel="alternate"; type="text/turtle;version=1.2"
```

Two headers, and **no minted vocabulary.** The `Content-Type` states the version served, which
the client did not ask for; `alternate` states where a complete representation is. Together they
make the loss non-silent, which is §6.2's requirement, without describing it.

That is the whole mechanism, and the restraint is deliberate. **A version is a property of the
representation as a whole, not of its parts.** Named graphs are separable components that carry
author-chosen names, so §6.2 can enumerate them with `containsGraph` and a client can act on
each. Version degradation is uniform: there are no parts, only a level. Describing *what* was
lost would mean describing a diff, and a diff is something a client obtains by fetching the
other representation — which `alternate` tells it how to do.

Considered and rejected: enumerating the affected predicates as `Link` headers, one minted
relation per response. It is complete (every triple has exactly one predicate, always an IRI)
and it survives blank nodes, unlike enumerating subjects — whose skolem IRIs are internal by
their own constraint rule and must never reach a header. It was dropped anyway, on a category
argument rather than a cost one: a `Link` target is a resource related to the context, and a
predicate IRI is a vocabulary term, not a component of the representation. §6.2's targets are at
least parts of the thing being served. These would not be.

Also considered and rejected: giving the omitted set its own URL. For named graphs that idea is
sound and is filed as [issue #4](https://github.com/tophcodes/sparql-pod/issues/4) — a named
graph is stable across reads and already carries a name. A version projection is not: the
omitted set is a function of *(resource state, requested version)*, so a URL naming it would
change referent on every write. That is a query result, not a resource, and content negotiation
is the mechanism for it.

Not recorded is **how much** was lost. Accepted: a client that needs the difference re-fetches
and has it exactly, rather than approximately.

## 6. Write: refusal, and the conflict that protects the read

| Case | Status |
|---|---|
| Body classifies richer than its declared `version` | **400** |
| Declared `version` exceeds what the store can hold | **415** |
| Unrecognised version label (`version=1.3`) | **415** |
| `PUT` below a resource's own classification (§3.1) | **409** |

`400` because the document contradicts its own declaration — this is a malformed request, not
an unsupported one.

`415` because `version` **is** a media-type parameter, and "I do not accept this media type" is
exactly what 415 says. It is also the status a client can act on once issue #3 lands, since
`Accept-Put` is the corresponding advertisement.

`409` is [datasets design](2026-07-28-jsonld-datasets-design.md) §6.2.1 a second time, and for
its exact reason. §5 hands a 1.1 client a lossy representation; without §6, `GET` as 1.1, edit,
`PUT` back would delete every triple term with a `2xx` and no warning. The read-side projection
must not become the template for its own destruction. The remedy is the same: send a `version=1.2`
representation, or `DELETE` first if replacement really is intended.

There is no `406` on the read side. A 1.1 request always gets an answer, only a poorer one.

## 7. What the type system must learn

A sharp result falls out of §2: **`Rdf12Basic` costs no type change at all.** A directional
literal *is* an `oxrdf::Literal`, and `GroundTerm::Literal` already accepts it. That is exactly
why it entered unnoticed. All of the following is about triple terms.

`dataset.rs` defines its own ground type family — `GroundQuad` over `GroundTerm`
(`NamedNode | Literal`) — which structurally cannot hold a triple term. Today
`Skolemized::skolemize` matches `Term::Triple(_)` with `unreachable!`, justified in its own
message by *"Format::parse refuses RDF 1.2 triple terms"*. This design removes that
justification, so the arm has to become real:

- **`GroundTerm` gains a recursive variant** (`Triple(Box<GroundTriple>)`). The ground family
  becomes recursive for the first time.
- **`skolemize` recurses**, and the property stated in its own doc comment must survive the
  recursion: *"no input can map to something that still holds a blank node."* A blank node in
  the subject of a triple term that slips through un-skolemized breaks both the round trip and
  the ETag, and it does so **silently**. This is the one place in this design where a mistake
  does not announce itself.
- **`deskolemize` recurses**, with the same label-derived-from-skolem-IRI rule, so reads stay
  stable across repetitions.
- **`from_store` accepts `Term::Triple` as ground.** It is documented as a *parse* of what the
  store hands back; if it keeps reading a triple term as non-ground, the pod reports its own
  correctly stored data as corruption.

## 8. What a store must be able to do — the §13 amendment

§13's fourth criterion reads today:

> Swapping Oxigraph for another SPARQL-1.1 store requires only config, no code change.

It names a product class and asserts a property of it. It has been untrue in a small way since
ADR-2, which records that the `;`-separated update sequence every write path depends on is a
property of `OxigraphStore` rather than of SPARQL. RDF 1.2 adds a second such property. The
criterion is restated to name capabilities:

> Swapping Oxigraph for another store requires only config, no code change — provided the
> replacement satisfies the capabilities the write path depends on: the SPARQL 1.1 Protocol,
> atomic `;`-separated update sequences (ADR-2), and the RDF version it declares
> (`SparqlStore::rdf_version`).

This is the design's actual payoff. It converts an implicit obligation and a new one into a
single enumerated list, so a second implementor has something to check itself against rather
than a sentence to contradict.

It is also what retires §4's premise that *"backend-pluggability and RDF-star are mutually
exclusive."* They are exclusive only while the criterion names a product class, because then a
store that cannot hold triple terms falsifies the whole claim. Once it names capabilities, such
a store is a configuration in which the pod declares `Rdf11` and refuses accordingly — a case
distinction, not a contradiction. This is the same graceful-degradation move §6.2 of the
datasets design makes for named graphs, one axis over.

A note on the deployment matrix this makes explicit, because the root spec is misleading about
it. §4 justifies the store choice with *"HTTP endpoint (not embedded) keeps multi-writer
(Windmill pipelines) and avoids the single-writer RocksDB constraint."* The implementation
embeds `oxigraph::store::Store`. The multi-writer rationale is therefore currently unmet — a
pre-existing divergence, out of scope here, recorded so ADR-6 does not appear to endorse it.
The matrix the capability list is written against is two implementors, not five: embedded
Oxigraph as the recommended default, and one generic client for any external SPARQL-1.1
endpoint. There is no second embeddable Rust quad store to be the third row.

## 9. Touched, but not changed

- **ETag.** §6.3 of the datasets design already made the selected *format* participate in the
  validator, because RFC 9110 §8.8.1 forbids one strong validator across differing
  representations. The **served version** joins it. Without that, the 1.1 projection and the
  1.2 representation share an ETag — the identical defect §6.3 fixed one axis earlier.
- **SHACL.** This design neither extends SHACL semantics nor claims `rudof` understands RDF
  1.2. Validation runs over the dataset as stored; a triple term is a term no shape matches. A
  named limitation, and no code.
- **WAC.** ACL documents travel the same write path, so an ACL containing triple terms would
  need `version=1.2`. `wac::pdp::decide` looks only at IRIs, so this is harmless and pointless.
  Recorded so that its absence is not later mistaken for an oversight.
- **`/sparql` read proxy.** Deferred (root spec §11). When it lands it inherits a version
  question from the *client* side — SPARQL 1.2 query syntax in submitted queries. Out of scope,
  named so the seam is not surprised by it.

## 10. Constraints

**Removed:** *"The wire contract is RDF 1.1, and it is checked rather than assumed."* Its check
(`rg -q 'Term::Triple\(_\)' src/rdf.rs`) pins a refusal this design deletes, and the rule was in
any case half true (§2).

**Added**, both in the one-site shape the existing rules use:

1. **The RDF version of a dataset is classified in exactly one place.** Two classifiers is how
   the write-side check and the read-side projection drift apart, and drift here is silent:
   both answer, one answers wrong. Same failure mode as the one-parser and one-negotiation
   rules already guard.
2. **The `version` media-type parameter is read in exactly one place.** `Content-Type` on write
   and `Accept` on read ask the same question of the same syntax; a second reader is how `1.2`
   comes to mean one thing on the way in and another on the way out.

`constraints.md`'s own preamble binds this design: each rule must be **demonstrated red against
a real violation** before it is added. A check that cannot fail is worse than no check.

## 11. Risks

1. **Whether the store round-trips a triple term. Task 0, with an abort criterion.** The pod
   talks to the store *only* in SPARQL strings, so storing triple terms means the store parses
   SPARQL 1.2. The feature layer is measured and holds: `oxigraph`'s `rdf-12` pulls in
   `spareval/sparql-12`, and this build resolves with both `spargebra feature "sparql-12"` and
   `spareval feature "sparql-12"` enabled. This was close to going the other way —
   `spargebra` has its own `sparql-12` feature that is **not** in its defaults, so
   `oxrdf/rdf-12` alone would have produced a pod that can read 1.2 off the wire and cannot
   write it into the store. §3.3's explicit declaration secures this chain too, since it is
   `oxigraph/rdf-12` that pulls `spareval/sparql-12` in. What remains unmeasured is behaviour: does
   `INSERT DATA { <s> <p> <<( <a> <b> <c> )>> }` execute and come back through `CONSTRUCT`, and
   does `oxttl` in fact parse a directional literal. If the first fails, this design is dead and
   ends as an ADR recording a refusal that was measured rather than assumed.
2. **Specification maturity** (§2.2). Turtle is a Working Draft one week old. Bounded by
   `oxttl` owning the grammar.
3. **Conformance.** The suite is a 1.1 client and under §4 never sees 1.2. A run still belongs
   in the plan, because `Content-Type: text/turtle;version=1.1` on a degraded response is new,
   and a strict equality check against `text/turtle` would fail on it.
4. **SHACL over 1.2** is unknown and not relied on (§9).

## 12. Testing

TDD throughout, as elsewhere in this project.

- Classification at all three levels, including a directional literal ⇒ `Rdf12Basic` — the case
  that is unrepresentable in today's check.
- A triple term round-trips through the store (Task 0).
- **A blank node inside a triple term** skolemizes, round-trips, and de-skolemizes stably
  across two reads. The silent-failure case from §7.
- 1.1 read of a 1.2 resource: the projection is correct, `Content-Type` carries
  `version=1.1`, and the `alternate` link names the resource's own classification — `1.2-basic`
  for a resource whose only excess is directional literals, not a blanket `1.2`.
- 1.1 `PUT` over a 1.2 resource ⇒ `409`.
- Unversioned `PUT` carrying a triple term ⇒ `400`.
- `version=1.2` `PUT` against an `Rdf11` store ⇒ `415`.
- The 1.1 projection and the 1.2 representation do not share an ETag.

## 13. Out of scope

- `Accept-Put` / `Accept-Post` advertisement — [#3](https://github.com/tophcodes/sparql-pod/issues/3).
- Addressable named graphs — [#4](https://github.com/tophcodes/sparql-pod/issues/4).
- A `RemoteSparqlStore` implementor. §3.2 specifies how it answers `rdf_version()`; building it
  is separate work, and `docs/constraints.md` still carries the one-implementor tripwire.
- SPARQL 1.2 on the `/sparql` read proxy (§9).
- Emitting or honouring the in-band `VERSION` directive (§2.2).
